# ТЗ: CZN Overlay Translator

Внешний переводчик игрового интерфейса Chaos Zero Nightmare.
Захват экрана → OCR → поиск в предзаполненной базе переводов → отрисовка поверх окна игры.

**Стек:** C# / .NET 8 (десктоп-часть), Python 3.11 (оффлайн-конвейер), SQLite, ONNX Runtime + DirectML.

---

## 0. Жёсткие ограничения

В игре стоит античит Wellbia (`ucldr`/`wldr` + `sparrow_x64.smt`), исполняемый файл упакован STOVE Shield, лаунчер сверяет MD5 файлов. Приложение **не должно иметь никакого контакта с процессом игры**.

**Запрещено категорически:**

- `OpenProcess`, `ReadProcessMemory`, `WriteProcessMemory`, `VirtualAllocEx`
- `CreateRemoteThread`, инжект DLL любым способом
- `SetWindowsHookEx` (глобальные хуки — выглядят как кейлоггер)
- Хук D3D/Present, оверлей через swapchain игры
- Запись любых файлов внутрь каталога игры
- Модификация `data.pack` или любых файлов клиента

**Разрешено:**

- Windows Graphics Capture — чтение композиции рабочего стола, тот же API, что у OBS и Discord
- `RegisterHotKey` — штатная регистрация горячих клавиш
- Чтение `data.pack` **только при закрытой игре**, только на чтение, через отдельный оффлайн-скрипт

Если при реализации возникает соблазн нарушить этот список — задача решается неправильно, нужно искать другой путь.

## 1. Архитектура

```
CznTranslator.sln
├─ CznTranslator.App          WPF host, tray, настройки, точка входа
├─ CznTranslator.Capture      WGC, D3D11, кроп и даунскейл на GPU
├─ CznTranslator.Detect       pHash зон, settle-таймер, приоритеты
├─ CznTranslator.Ocr          ONNX Runtime + DirectML, det + rec
├─ CznTranslator.Lookup       SQLite, нормализация, точный и нечёткий поиск
├─ CznTranslator.Overlay      DirectComposition + Direct2D, click-through
├─ CznTranslator.Sync         watcher data.pack, клиент Ollama, фолбэк
└─ CznTranslator.Core         модели данных, конфиг, логи, метрики
```

Поток данных:

```
WGC frame (GPU)
  → crop ROI + grayscale + resize (compute shader, на GPU)
  → pHash 64px (readback только хэша)
  → [изменилось?] → settle 100 мс → [стабильно?]
  → readback ROI (только кроп, не весь кадр)
  → det ONNX → line boxes → rec ONNX → строки
  → normalize → lookup(exact → fuzzy → LLM)
  → overlay draw
```

Пакеты: `Vortice.Windows` (D3D11/D3D12/D2D/DComp), `Microsoft.Windows.CsWinRT` (WGC),
`Microsoft.ML.OnnxRuntime.DirectML`, `OpenCvSharp4` (постобработка det),
`Microsoft.Data.Sqlite`, `Serilog`.

> `Microsoft.ML.OnnxRuntime.DirectML` конфликтует с базовым `Microsoft.ML.OnnxRuntime` — ставить **только** DirectML-пакет, иначе получишь конфликт нативных DLL в выходной папке.

## 2. Capture

**API:** `Windows.Graphics.Capture`. Получение `GraphicsCaptureItem` для конкретного окна — программно, через `IGraphicsCaptureItemInterop.CreateForWindow(hwnd)`, без системного пикера.

Поиск окна игры: по имени процесса + классу окна, с ретраями раз в 2 секунды, пока игра не запущена.

Настройки сессии:

- `IsCursorCaptureEnabled = false`
- `IsBorderRequired = false` — доступно с Windows 11 22H2, проверять через `ApiInformation.IsPropertyPresent`, иначе жёлтая рамка захвата
- `Direct3D11CaptureFramePool.CreateFreeThreaded` — обработка вне UI-потока
- Формат `B8G8R8A8UIntNormalized`, 2 буфера

**Ключевой момент производительности:** кадр приходит как `ID3D11Texture2D` и остаётся на GPU. Кроп нужной зоны, перевод в grayscale и ресайз делаются compute-шейдером **до** копирования в RAM. На CPU уезжает только маленький ROI (типично 400×80 px), а не весь кадр 2560×1440. Это главный выигрыш архитектуры — не экономь на нём.

Игра должна работать в **borderless windowed**. В exclusive fullscreen WGC отдаёт чёрные кадры — это документированное поведение, обрабатывать как ошибку с понятным сообщением пользователю, а не молча.

## 3. Detect

OCR не запускается на каждом кадре. Регулятор — детектор изменений.

**Зоны** описываются в конфиге в нормализованных координатах (0..1 от размера окна), чтобы не ломаться при смене разрешения:

```json
{
  "zones": [
    { "id": "dialogue", "rect": [0.15, 0.72, 0.70, 0.20], "priority": 0, "mode": "block" },
    { "id": "tooltip",  "rect": [0.00, 0.00, 1.00, 1.00], "priority": 1, "mode": "auto" },
    { "id": "topbar",   "rect": [0.00, 0.00, 1.00, 0.08], "priority": 2, "mode": "line" }
  ]
}
```

**Алгоритм на каждый кадр (60 fps):**

1. Для каждой зоны: даунскейл до 64×64 на GPU, readback 4 КБ, DCT-based pHash (64 бита).
2. `hamming(hash, prevHash) > 4` → зона грязная, сбросить settle-таймер.
3. Хэш стабилен `settleMs` (по умолчанию 100, диапазон 60–200) → зона готова к OCR.
4. Перед OCR проверить `zone_cache[zoneHash]` — если экран уже видели, отдать готовый результат мгновенно, без распознавания.
5. Иначе поставить в очередь OCR с учётом `priority`.

Очередь OCR — одна, с приоритетами, максимум один инференс одновременно. Зона с `priority: 0` вытесняет фоновые.

`settleMs` вынести в настройки с живым применением — его придётся подбирать под анимации игры вручную.

## 4. OCR (DirectML)

**Модели:** ONNX-порты PaddleOCR из проекта RapidOCR.

| Роль | Модель | Вход |
|---|---|---|
| Детекция | `ch_PP-OCRv4_det_infer.onnx` | динамический, стороны кратны 32 |
| Распознавание | `en_PP-OCRv4_rec_infer.onnx` + `en_dict.txt` | H=48, W динамический |

Детектор языконезависим — он ищет прямоугольники с текстом. Классификатор угла (`cls`) **не подключать**: интерфейс игры горизонтальный, а это лишние 3–5 мс на строку.

**Инициализация сессии:**

```csharp
var so = new SessionOptions();
so.AppendExecutionProvider_DML(deviceId);
so.EnableMemoryPattern = false;          // обязательно для DML
so.ExecutionMode = ExecutionMode.ORT_SEQUENTIAL;  // обязательно для DML
so.GraphOptimizationLevel = GraphOptimizationLevel.ORT_ENABLE_ALL;
```

Первый инференс включает компиляцию шейдеров и занимает 1–3 секунды — прогреть обе модели пустышками при старте приложения, до показа окна.

**Препроцессинг det:** ресайз с сохранением пропорций до кратности 32, нормализация `mean=[0.485,0.456,0.406]`, `std=[0.229,0.224,0.225]`.

**Постобработка det (DB):** бинаризация карты вероятностей по порогу 0.3 → `Cv2.FindContours` → `MinAreaRect` → расширение бокса по unclip ratio 1.6 → фильтр по минимальной площади. Всё через OpenCvSharp.

**Препроцессинг rec:** кроп по боксу, ресайз до H=48 с сохранением пропорций, нормализация в `[-1, 1]` (`mean=0.5, std=0.5`). Строки одной высоты батчить вместе с паддингом по ширине — это заметно быстрее поштучного прогона.

**Постобработка rec:** greedy CTC-декодирование, схлопывание повторов, выброс blank-токена. Складывать среднюю уверенность по символам — она понадобится для порога нечёткого поиска.

**Целевая задержка:** det + rec на зоне 400×80 с 3 строками — 15–30 мс на среднем GPU.

### Выбор провайдера

`IOcrBackend` с двумя реализациями — `DmlOcrBackend` и `CpuOcrBackend`. Выбор при старте, каскадом:

1. Перечислить адаптеры через `DXGI.CreateDXGIFactory1().EnumAdapters1()`, отсортировать по `DedicatedVideoMemory` убыванием, отбросить `DXGI_ADAPTER_FLAG_SOFTWARE` (WARP).
2. Взять первый подходящий → `AppendExecutionProvider_DML(index)`.
3. Провайдер не инициализировался или адаптеров нет → `CpuOcrBackend`.

Выбранный бэкенд и имя адаптера писать в лог и показывать в трее. Принудительное переключение — `"ocr.provider": "auto" | "dml" | "cpu"` и `"ocr.adapterIndex"` в конфиге.

Встроенная графика (Intel Iris Xe, AMD Radeon Graphics) поддерживает DirectML полноценно, поэтому на ноутбуке первым делом пробуется именно она — 40–70 мс против 120–250 мс на CPU. До `CpuOcrBackend` дело доходит только на машинах без пригодного адаптера вообще.

## 5. Lookup

### Схема БД

```sql
CREATE TABLE strings (
  id           INTEGER PRIMARY KEY,
  key          TEXT,               -- ключ из data.pack, NULL для OCR-only строк
  table_name   TEXT,               -- имя исходной таблицы дампа
  en           TEXT NOT NULL,
  ru           TEXT,
  norm         TEXT NOT NULL,      -- нормализованный en
  norm_hash    INTEGER NOT NULL,   -- xxHash64 от norm
  status       TEXT NOT NULL,      -- new | mt | reviewed | locked | stale
  src          TEXT NOT NULL,      -- pack | ocr | manual
  pack_version INTEGER,
  updated_at   INTEGER
);
CREATE INDEX idx_norm_hash ON strings(norm_hash);
CREATE UNIQUE INDEX idx_key ON strings(key) WHERE key IS NOT NULL;

CREATE VIRTUAL TABLE strings_fts USING fts5(
  norm, content='strings', content_rowid='id', tokenize='trigram'
);

CREATE TABLE glossary (
  en TEXT PRIMARY KEY, ru TEXT NOT NULL,
  locked INTEGER DEFAULT 0, note TEXT
);

CREATE TABLE ocr_corrections (
  raw_norm TEXT PRIMARY KEY, string_id INTEGER NOT NULL,
  hits INTEGER DEFAULT 1
);

CREATE TABLE zone_cache (
  zone_hash INTEGER PRIMARY KEY, payload TEXT NOT NULL,
  hits INTEGER DEFAULT 1, last_seen INTEGER
);

CREATE TABLE pack_versions (
  version INTEGER PRIMARY KEY, pack_md5 TEXT NOT NULL,
  ripped_at INTEGER, note TEXT
);

CREATE TABLE metrics (
  day TEXT PRIMARY KEY, ocr_calls INTEGER, cache_hits INTEGER,
  fuzzy_hits INTEGER, llm_calls INTEGER, misses INTEGER, avg_ms REAL
);
```

### Нормализация

Одна функция, используется **и** при импорте дампа, **и** при обработке OCR — иначе базы не сойдутся:

1. lowercase, trim, схлопывание пробелов
2. унификация похожих глифов: `l|I|1|¦ → 1`, `O|0 → 0`, `S|5 → 5`, `B|8 → 8`
3. удаление пунктуации и небуквенных символов, кроме плейсхолдеров `{0}`
4. вырезание разметки: `<color=...>`, `</color>`, спрайт-теги, `\n`

### Каскад поиска

1. **`ocr_corrections`** по `raw_norm` — подтверждённые ранее правки, мгновенно.
2. **Точное совпадение** по `norm_hash` — хэш-индекс, микросекунды.
3. **Нечёткий поиск:** FTS5 trigram даёт топ-50 кандидатов → нормализованное расстояние Левенштейна в C# → лучший результат при score ≥ 0.85.
   Порог динамический: при средней уверенности OCR ниже 0.7 опускать до 0.80.
4. **Промах** → фолбэк в Ollama (см. §7), результат пишется в `strings` с `src='ocr'`, чтобы в следующий раз попасть на шаге 2.

Результат зоны целиком кладётся в `zone_cache` по её pHash.

## 6. Overlay

Окно: `WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOPMOST | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE | WS_EX_NOREDIRECTIONBITMAP`.

Отрисовка через **DirectComposition + Direct2D**, не через `UpdateLayeredWindow`. Второй способ гоняет битмап через CPU и на 1440p даёт заметные просадки.

Поведение:

- Полностью click-through, никакого перехвата ввода
- Позиция и размер синхронизируются с окном игры (`SetWinEventHook` на `EVENT_OBJECT_LOCATIONCHANGE` для целевого HWND — это не глобальный хук, а подписка на события конкретного окна, для античита безопасно)
- Скрывается, когда игра теряет фокус или сворачивается
- Русский текст рисуется на полупрозрачной подложке поверх оригинала; шрифт свой, поэтому проблема кириллицы здесь не существует
- Автоподбор кегля: если перевод не влезает в бокс оригинала — уменьшать до 0.8×, дальше переносить по словам, дальше обрезать с многоточием и показывать полный текст по наведению (в режиме hold-hotkey)

Горячие клавиши через `RegisterHotKey`:

| Клавиша | Действие |
|---|---|
| `Ctrl+Alt+T` | вкл/выкл оверлей |
| `Ctrl+Alt+A` | разовый перевод выделенной мышью области |
| `Ctrl+Alt+R` | сбросить `zone_cache` (после патча) |
| `Ctrl+Alt+D` | debug-режим: рамки зон, боксы OCR, задержки |

## 7. Sync и фолбэк

### Watcher

При старте приложения (игра закрыта) — MD5 файла `data.pack`. Не совпал с последним в `pack_versions` → показать уведомление «вышел патч, требуется обновление базы» и предложить запустить конвейер. Автоматически ничего не пересобирать.

### Фолбэк-перевод в рантайме

Ollama на домашнем сервере через Tailscale, модель `qwen3-loc` (см. §8). Таймаут 3 с, при недоступности — показать оригинал, записать промах в метрики. Очередь фолбэков — не более 2 параллельных запросов, чтобы не забить сервер.

Результаты фолбэка помечаются `status='mt'` и попадают в очередь ревью.

## 8. Оффлайн-конвейер (Python)

Отдельная папка `tools/`, запускается вручную при закрытой игре.

```
tools/
├─ import_dump.py    JSON от ASSet Ripper → таблица strings
├─ diff_pack.py      сравнение версий, разметка new/changed/stale
├─ translate.py      батч-перевод через Ollama
├─ validate.py       проверка плейсхолдеров, тегов, длины
├─ review.py         локальный веб-UI для утверждения переводов
└─ glossary.yaml     термины и имена
```

> **Важно:** ASSet Ripper на текущий момент GUI-only, экспорт делается руками. `import_dump.py` работает по уже выгруженной папке. Автоматизация экспорта — отдельная задача (репозиторий под MIT, C++, headless-режим добавляется правкой `main.cpp`), в первую версию не входит.

### Поиск таблиц локализации

Дамп содержит десятки JSON. Эвристика для отбора: доля значений, похожих на английские предложения (латиница + пробелы + длина > 3 слов) выше 60%, либо имя файла/поля содержит `locale`, `text`, `string`, `desc`, `name`, `lang`.

Результат отбора писать в `tools/tables.yaml` — дальше файл правится руками и используется как источник истины.

### Батч-перевод

Батчи по 40 строк, JSON на входе и выходе. Системный промпт:

```
Ты переводчик игровой локализации. Переводишь с английского на русский
интерфейс и сюжетные тексты тёмного фэнтези-рогалика.

Правила:
- Сохраняй ВСЕ плейсхолдеры ({0}, {value}, %s) и теги (<color=...>, </color>,
  <sprite=...>) точно как в оригинале, включая порядок.
- Соблюдай глоссарий дословно, без склонений имён собственных в базовой форме.
- Интерфейсные строки — коротко, в стиле игровых кнопок, без точки в конце.
- Не добавляй пояснений, не переводи то, что выглядит как техническое ID.
- Если строка непереводима (код, число, пустая) — верни её без изменений.

Глоссарий:
{glossary}

Отвечай ТОЛЬКО валидным JSON-массивом вида [{"id": <int>, "ru": "<перевод>"}].
Без markdown, без пояснений.
```

Перед вызовом модели — проверка translation memory: если такой же `norm` уже переведён под другим ключом, взять готовое. В гачах дублей 20–40%.

### Валидатор

Строка отправляется в ревью, если:

- набор плейсхолдеров или тегов не совпал с оригиналом
- длина перевода больше 1.6× оригинала (не влезет в интерфейс)
- в переводе нет кириллицы, хотя в оригинале были буквы
- модель вернула невалидный JSON (весь батч на повтор)

### Diff при патче

```
new       → перевести
changed   → пометить stale, старый ru сохранить как фолбэк, перевести заново
removed   → не удалять, пометить, пригодятся при откате
unchanged → не трогать
```

Версия пака инкрементируется, старые строки остаются в базе.

## 9. Конфигурация и метрики

`config.json` рядом с исполняемым файлом, живое применение без перезапуска для: `settleMs`, порогов поиска, зон, размера шрифта, прозрачности.

Метрики в БД посуточно, отображение в трее:

- **coverage** = `(cache_hits + exact + fuzzy) / ocr_calls` — главный показатель. Норма выше 90%. Падение после патча означает, что база устарела.
- p50/p95 задержки по этапам: capture, ocr, lookup, draw
- количество промахов и ушедших в LLM

Логи — Serilog, ротация по дням, уровень из конфига.

## 11. Подводные камни

- **Exclusive fullscreen** ломает и захват, и оверлей. Проверять режим окна на старте, писать явное сообщение.
- **DPI.** Приложение должно быть per-monitor DPI aware v2, иначе координаты зон разъедутся на масштабировании отличном от 100%.
- **Первый инференс DML** — 1–3 секунды. Прогрев обязателен, иначе первый перевод в сессии будет выглядеть как зависание.
- **Анимации fade-in.** Слишком маленький `settleMs` → OCR ловит полупрозрачный текст и выдаёт мусор. Симптом: низкая уверенность распознавания и промахи поиска на знакомых экранах.
- **Скроллящиеся списки** генерируют новый pHash каждый кадр и забьют очередь OCR. Для таких зон — режим `mode: "manual"`, только по горячей клавише.
- **Разные разрешения.** Все координаты хранить нормализованными, никаких абсолютных пикселей в конфиге.
- **FTS5 trigram** требует SQLite 3.34+. Проверить версию нативной библиотеки в `Microsoft.Data.Sqlite`, при необходимости взять `SQLitePCLRaw.bundle_e_sqlite3`.

## 12. Профиль ноутбука

Ветка для разработки и тестирования на слабой машине, в том числе без установленной игры. Включается профилем `"profile": "laptop"` в конфиге — это набор переопределений, а не отдельная сборка.

**Целевая машина:** MSI Prestige 13 Evo A13M — Intel 13-го поколения P-серии, графика Intel Iris Xe, дискретного GPU нет.

Iris Xe поддерживает DirectML полноценно, поэтому основной путь на ноутбуке — **тот же `DmlOcrBackend`**, каскад из §4 остановится на встроенном адаптере. Ожидаемая задержка det + rec на зоне 400×80 — 40–70 мс. `CpuOcrBackend` остаётся аварийным вариантом для машин без пригодного адаптера и в штатной работе не задействуется.

Два следствия из того, что графика встроенная:

- **Узкое место — пропускная способность памяти, а не вычисления.** iGPU делит системную RAM с CPU, поэтому int8-модели из таблицы ниже нужно оставить включёнными даже на DML-пути: они сокращают трафик к памяти и дают заметный выигрыш, хотя на дискретной карте разница была бы в пределах шума.
- **Тепловой пакет 28 Вт в корпусе 13″.** Под длительной нагрузкой частоты падают, поэтому непрерывный опрос экрана на этой машине бессмысленен. Штатный режим отладки — `FolderFrameSource` (см. ниже) и ручной прогон по горячей клавише, а не живой захват.

### CpuOcrBackend

Один NuGet-пакет `Microsoft.ML.OnnxRuntime.DirectML` покрывает оба случая: CPU EP скомпилирован в любую сборку ORT и работает, если просто не вызывать `AppendExecutionProvider_DML`. Второй пакет ставить не нужно и **нельзя** — будет конфликт нативных DLL.

Опции сессии для CPU — противоположные тем, что требует DML, так что общий код настройки не годится, нужны раздельные ветки:

```csharp
var so = new SessionOptions();
so.EnableMemoryPattern = true;                      // на CPU наоборот полезно
so.ExecutionMode = ExecutionMode.ORT_PARALLEL;
so.IntraOpNumThreads = physicalCores;               // физические ядра, не логические
so.InterOpNumThreads = 2;
so.GraphOptimizationLevel = GraphOptimizationLevel.ORT_ENABLE_ALL;
```

`IntraOpNumThreads` по числу **физических** ядер (`Win32_Processor.NumberOfCores` через WMI). Отдавать ORT логические потоки с hyperthreading — стабильно хуже, проверено на многих бенчмарках.

> **Гибридная архитектура.** У процессоров Intel 12-го поколения и новее ядра делятся на производительные (P) и энергоэффективные (E), и `NumberOfCores` считает их вместе. Пул потоков ORT синхронизируется по самому медленному участнику, поэтому E-ядра тормозят весь инференс. Если CPU-путь всё же понадобится — считать только P-ядра и привязывать потоки через `so.AddSessionConfigEntry("session.intra_op_thread_affinities", ...)`. На целевом ноутбуке это, скорее всего, мёртвый код, но при слепом использовании `NumberOfCores` разница достигает полутора раз.

### Модели и параметры

| Параметр | Профиль GPU | Профиль ноутбука |
|---|---|---|
| Модели | `*_infer.onnx` (fp32) | `*_infer_quant.onnx` (int8, из RapidOCR) |
| `det.limitSideLen` | 960 | 640 |
| `settleMs` | 100 | 220 |
| Зоны в режиме `auto` | все | только `priority: 0` |
| pHash-опрос | каждый кадр | каждый 4-й кадр (15 Гц) |
| Батчинг rec | до 8 строк | до 4 строк |

Int8-квантованные модели дают на CPU ускорение примерно вдвое ценой 1–3% точности распознавания — на игровом интерфейсе с крупным контрастным шрифтом эта потеря не проявляется, порог нечёткого поиска её поглощает.

Ожидаемая задержка на ноутбучном CPU: det 80–150 мс, rec 15–25 мс на строку. Итого 150–250 мс на зону. Играть с этим некомфортно, но для отладки логики достаточно.

### Оффлайн-стенд

Главная ценность профиля — возможность разрабатывать всё, кроме захвата, на машине без игры.

`IFrameSource` с двумя реализациями:

- `WgcFrameSource` — боевая
- `FolderFrameSource` — читает PNG из `testdata/frames/` по таймеру, отдаёт как кадры

Конфиг: `"capture.source": "wgc" | "folder"`, `"capture.folder": "testdata/frames"`, `"capture.fps": 2`.

`testdata/` наполняется скриншотами игры, снятыми на основной машине. Рядом с каждым PNG — опциональный `.expected.json` с ожидаемым результатом OCR и поиска.

Это же даёт регрессионный тест: `dotnet test` прогоняет весь набор через пайплайн и сверяет с эталонами. Любая правка нормализации или порогов поиска сразу показывает, что сломалось. Держать в наборе не меньше 30 кадров, включая проблемные — полупрозрачный текст, мелкий шрифт, цветные теги.

Оверлей в этом режиме рисуется поверх собственного окна-заглушки с текущим кадром, чтобы визуально проверять раскладку и подбор кегля.

### Критерии приёмки профиля

Отличаются от основных (§10) только задержкой: p95 «изменение кадра → отрисованный перевод» ≤ 600 мс. Coverage, корректность поиска и стабильность — те же, они от железа не зависят.
