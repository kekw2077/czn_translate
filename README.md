# CZN Overlay Translator

Внешний переводчик интерфейса Chaos Zero Nightmare: захват экрана → OCR → поиск в
предзаполненной базе → отрисовка поверх окна игры.

Реализация по [ТЗ](docs/TZ_CZN_Overlay_Translator.md). Ссылки вида «§4» ниже — на разделы ТЗ.

## Главное ограничение

В игре стоит античит Wellbia, исполняемый файл упакован STOVE Shield, лаунчер сверяет MD5.
Приложение **не имеет никакого контакта с процессом игры** (§0). В коде нет и не должно
появиться `OpenProcess`, `ReadProcessMemory`, `CreateRemoteThread`, инжекта DLL,
`SetWindowsHookEx`, хука D3D/Present и записи чего-либо в каталог игры.

Три места, где легко ошибиться, и почему выбрано именно так:

- **Захват** — `Windows.Graphics.Capture`, тот же публичный API, что у OBS и Discord. Читается
  композиция рабочего стола, а не игра.
- **Слежение за окном** — `SetWinEventHook`, ограниченный процессом игры и работающий
  out-of-context. Это подписка на события одного окна, а не глобальный хук: ничего никуда не
  внедряется. Именно поэтому §0 запрещает `SetWindowsHookEx`, а §6 разрешает `SetWinEventHook`.
- **Горячие клавиши** — `RegisterHotKey`. Оболочка доставляет `WM_HOTKEY` конкретному окну,
  приложение не видит ничего другого.

Единственный файл игры, к которому вообще обращается код, — `data.pack`, только на чтение,
только при закрытой игре, только чтобы посчитать MD5 (§7).

## Как это работает

```
WGC frame (GPU)
  → crop ROI + grayscale + resize (compute shader, на GPU)
  → pHash 64px (readback только хэша, 4 КБ на зону)
  → [изменилось?] → settle → [стабильно?]
  → zone_cache по pHash → если есть, отрисовать без OCR
  → readback ROI (только кроп)
  → det ONNX → боксы → rec ONNX → строки
  → normalize → lookup(corrections → exact → fuzzy → LLM)
  → overlay draw
```

Порядок здесь — не оформление, а суть. Кадр не покидает GPU, пока зона не изменилась и не
устоялась; кэш проверяется **до** OCR, а не после; одновременно выполняется ровно один инференс.
`TranslationPipeline` существует именно чтобы удерживать эти инварианты.

## Решения, о которых стоит знать

Всё ниже — либо отступление от буквы ТЗ, либо выбор в месте, где ТЗ оставляет свободу.
Каждое зафиксировано тестом.

**Схема БД дополнена тремя вещами** (`tools/schema.sql`, всё аддитивно):

- триггеры синхронизации `strings_fts`. FTS5 с `content='strings'` сама не наполняется —
  без них индекс пуст, и нечёткий поиск молча не находит ничего;
- `metrics.exact_hits` — §9 определяет coverage через точные попадания, а вывести их из
  остальных колонок нельзя;
- `schema_meta` для версии схемы.

**Формула coverage.** §9 записывает её как `(cache_hits + exact + fuzzy) / ocr_calls`, но
попадание в кэш по определению не доходит до OCR, поэтому `ocr_calls` не может быть знаменателем —
на хорошо закэшированной сессии величина вышла бы больше единицы. В знаменателе стоит число всех
разрешений строки, включая кэш; именно про эту величину и говорит порог в 90%.

**Порядок нормализации.** §5 перечисляет шаги как «пунктуация, потом разметка», но снятие тегов
обязано идти первым: иначе `<color=#ff0000>` превращается в слова «color ff0000» и загрязняет
каждую строку с форматированием. Плейсхолдеры защищены от свёртки глифов — иначе `{value}`
станет `{va1ue}`, и импортёр с OCR-путём разойдутся на всём параметризованном.

**`settleMs`.** §3 называет диапазон 60–200 мс, §12 ставит ноутбучному профилю 220. Валидатор
принимает оба и предупреждает только за пределами 60–260, чтобы не кричать на каждом старте
ноутбука.

**Профиль применяется как значения по умолчанию, а не как принудительные.** Переопределение
ложится только туда, где `config.json` про этот ключ ничего не сказал. `"profile": "laptop"`
вместе с явным `settleMs: 120` оставляет 120 — иначе это был бы не «набор переопределений», а
вторая сборка.

**Подсчёт ядер — `GetLogicalProcessorInformationEx`, а не WMI.** ТЗ предлагает
`Win32_Processor.NumberOfCores` и тут же предупреждает, что на гибридных CPU это число считает
P- и E-ядра вместе. Этот API отдаёт класс эффективности на каждое ядро, так что P-ядра
**считаются**, а не угадываются, и System.Management не нужен.

**Уверенность CTC усредняется только по шагам, давшим символы.** Усреднение по всем шагам
позволило бы длинной череде уверенных blank-ов раздуть оценку плохо прочитанной строки — а от
этого числа зависит выбор порога нечёткого поиска.

**Вытесненная задача OCR возвращается в очередь, а не отбрасывается.** Детектор сообщает об
устоявшейся зоне ровно один раз, так что отброшенная задача оставила бы экран без перевода до
следующего изменения. `maxPreemptions` ограничивает возвраты, чтобы активная зона с
`priority: 0` не заморозила фон навсегда.

**Эталонный хэш зоны не обновляется при дрейфе ниже порога.** Обновление на каждом кадре
позволило бы медленному fade-in уехать сколь угодно далеко, ни разу не сработав, — ровно тот
сценарий, о котором предупреждает §11.

**Удалённые строки помечаются `pack_version` ниже текущей, а не новым статусом.** §8 требует их
сохранить, а перечисление статусов в §5 не содержит `removed`; так не нужна миграция схемы, и
строки не попадают в очередь перевода.

**Изменённая строка сохраняет старый `ru`, уходя в `stale`.** Он неверен для нового английского,
но лучше показывать его, чем сырой английский, пока не приедет новый перевод.

**Память переводов переиспользует только `reviewed` и `locked`.** Переиспользование чужой
машинной догадки размножило бы её по базе вместо того, чтобы её поймать.

**Батч с недостающими id проваливается целиком.** Молча потерянная строка через три шага
неотличима от той, которую модель намеренно вернула без изменений.

## Оффлайн-конвейер

### Сначала — разведка

ТЗ (§8) предполагает, что тексты лежат в Unity-ассетах и выгружаются AssetRipper-ом в JSON. Это
верно не всегда: корейские гачи часто держат мастер-данные в SQLite — отдельным файлом или
приклеенным внутрь `data.pack`. Прежде чем что-то парсить, стоит выяснить, что там на самом деле:

```bash
cd tools
python probe_pack.py --path "C:/Games/CZN"
```

Скрипт определяет формат каждого файла по сигнатуре (SQLite, UnityFS, zip, gzip, zstd, lz4,
JSON/CSV/XML), считает энтропию, чтобы отличить сжатое или зашифрованное от просто незнакомого, и
заодно ищет **базы, вложенные в контейнеры**. Последнее — главное: если `data.pack` собран простой
конкатенацией, базы достаются оттуда дословно, не разбираясь в формате архива вообще.

```bash
python probe_pack.py --path "C:/Games/CZN/data.pack" --carve --out ./carved
```

Одной сигнатуры для этого мало: шестнадцать байт ASCII `SQLite format 3` попадаются и внутри
сжатых данных, и в любом файле, который просто упоминает SQLite. Поэтому проверяется весь
заголовок — размер страницы (степень двойки в 512..32768 либо escape-значение 1), версии
чтения/записи, и что счётчик страниц не выходит за конец файла. Без этих проверок carve возвращал
бы в основном мусор.

Дальше — по результату:

- нашлась база → `import_dump.py --scan` предложит её таблицы;
- только контейнеры → распаковать, потом сканировать;
- всё высокоэнтропийное → пак упакован или зашифрован, ни один путь не работает, пока это не снято;
- ни того ни другого → тексты, скорее всего, в Unity-ассетах, и путь через AssetRipper из §8 верный.

### Два источника, один путь

`tables.yaml` описывает и JSON-таблицы, и таблицы БД, а всё ниже по течению — импорт, diff,
перевод, валидация — не знает, откуда пришли строки:

```yaml
tables:
  - kind: json
    file: LocaleTable.json
    path: entries[].text
    key_path: entries[].key
    include: true

  - kind: sqlite
    file: masterdata.db
    table: StringTable
    text_column: en
    key_column: key
    include: true
```

Сканер понимает обе раскладки, которые встречаются на практике: **широкую** (строка на запись,
колонка на язык — `key | ko | en | ja`) и **высокую** (строка на запись *и* язык — `key | lang |
text`). Во второй он сам находит колонку языка и значение, означающее английский, и считает
«похожесть на предложения» только по английским строкам — иначе таблица, где две трети содержимого
корейские и японские, провалилась бы по порогу и была бы отброшена.

Подсказка по имени учитывается только от **колонки**, не от таблицы. Таблица `StringTable`
содержит «string», и подсказка на уровне таблицы затянула бы в импорт и колонку ключей, и
корейский с японским. Импорт чужого языка как исходного английского отравил бы всю базу, а заметить
это в длинном `tables.yaml` тяжело. Подсказка на уровне таблицы по-прежнему поднимает кандидата
выше в списке — просто больше ничего не решает.

Игровая БД открывается через `file:...?mode=ro`, то есть SQLite сам отказывается писать в неё
(§0). Отклонённые кандидаты остаются в `tables.yaml` вместе с их долей и примерами — таблицу,
которую эвристика пропустила, проще найти глазами в списке, чем перезапуская скан с другими
порогами.

### Перевод: маскировка разметки

Отдавать переводчику `<#F9385D>Deal $Fixed Damage$ to all</>` и просить не сломать теги — это
лотерея, и на 60 тысячах строк она обязательно проигрывает. `extract_text.py` вместо этого
вынимает разметку и подставляет нумерованные метки:

```
'<#F9385D>Deal $Fixed Damage$ to all</>'
  ->  '[0]Deal [1] to all[2]'        переводчик видит только это
  ->  '[0]Наносит [1] всем[2]'       и возвращает это
  ->  '<#F9385D>Наносит $Фикс. урон$ всем</>'
```

Маркеры делятся на три группы и обрабатываются по-разному:

- **структурные** (`<...>`, `{0}`, `#var#`, `[shake]`, `%s`) — замкнутое множество ~640 штук на
  всю игру, переводчик их вообще не видит;
- **ключевые слова** (`$Shield$`, `$Discard Pile$`) — 520 терминов, чьё *содержимое* переводится
  один раз через глоссарий, чтобы текст правил был согласован;
- **`<br>`** — граница сегмента, а не маркер: половинки переводятся отдельно.

Порядок альтернатив в регулярке несущий: `<...>` идёт первым, иначе `$` внутри `<$shake>`
открывает ключевое слово и съедает предложение до следующего `$`.

```bash
python extract_text.py --source all_en.json --seed all_ru_clean.json --out-dir translate_out
#   glossary_terms.txt   520 терминов — перевести первыми
#   part_001.txt ...     текст по сегменту на строку, порциями под веб-переводчик
#   segments_ru.json     память переводов

# перевести файлы, сохранить рядом как part_001.ru.txt с тем же числом строк

python apply_text.py --source all_en.json --out-dir translate_out --output all_ru.json
```

Ничего не принимается на веру. Если метка не вернулась — сегмент остаётся английским и попадает
в отчёт: потерянный `</>` оставит цветовой диапазон открытым и перекрасит весь экран дальше, это
хуже одной непереведённой строки. Если переводчик склеил строки и их число не сошлось — вся
порция пропускается целиком, потому что сопоставление идёт по позиции и сдвиг испортил бы всё
после места склейки.

Повторный запуск инкрементален: в `part_*.txt` попадает только то, чего нет в памяти, так что
после патча переводится ровно новое.

`--seed` принимает готовый `en -> ru` и складывает его в память, но берёт только те записи, чей
исходник действительно без разметки. Строка с маркерами, переведённая чем-то, что маркеров не
видело, отбрасывается и уходит в очередь заново — именно так `$Discard Pile$` превращается в
«доллары США».

### Станция перевода

Станция — это то, что собственно переводит: коробка с Ollama, домашний сервер через Tailscale
или человек с папкой и веб-переводчиком. Она видит **только замаскированный текст**, поэтому
сломать игровую разметку не может в принципе — ей нечего ломать. Единственное её обязательство —
сохранить метки `[0]`, и это проверяется на возврате.

```bash
python translate_station.py --check                      # проверить связь
python translate_station.py --source all_en.json         # прогнать всё, что осталось
python apply_text.py --source all_en.json                # собрать строки с разметкой
```

`station.json` рядом со скриптами:

```json
{ "kind": "ollama", "endpoint": "http://192.168.1.50:11434", "model": "qwen2.5:7b-instruct", "batch": 25 }
```

Хост — просто URL, поэтому localhost и машина через Tailscale устроены одинаково. Если сетевого
пути нет вовсе — `{"kind": "folder", "folder": "station_dropbox"}`: программа кладёт
`request_001.txt`, станция (скрипт или человек) оставляет рядом `request_001.ru.txt`. Тот же
контракт, что и у ручного веб-переводчика, так что одна папка работает в обоих случаях.

Проверки на возврате одинаковы для обоих транспортов:

- набор меток должен совпасть с исходным — не только наличие, но и количество: `[0]` дважды
  вклеит один и тот же тег в два места;
- батч, вернувшийся не тем числом элементов, не «подрезается» — иначе переводы съедут на
  соседние строки. Такой батч переигрывается построчно;
- сегмент, потерявший метку после всех попыток, не попадает в память: он уходит в
  `station_failed.txt` на второй заход или ручной перевод.

Результаты складываются в тот же `segments_ru.json`, что и ручной файловый маршрут, — их можно
свободно смешивать: основной объём через станцию, остаток руками.

### Импорт готового словаря в базу

```bash
python import_pairs.py --pairs all_ru.json --db ../czn.db
```

Самый короткий путь к работающему оверлею: пары уже покрывают текст игры, поэтому ни экспорта
AssetRipper, ни вырезания баз из пака для *строк* не требуется.

**Разметка по умолчанию снимается, и это осознанно.** `all_ru.json` хранит теги, потому что они
нужны для подмены строк внутри игры. Оверлей — другой потребитель: он рисует `ru` своим шрифтом,
и сохранённый `<#FFFBC9>` появится на экране этими самыми символами. OCR разметки тоже никогда не
видит — он читает уже отрисованную строку. Так что в базу едет отображаемый текст. `--keep-markup`
сохраняет сырой вид.

Что при этом происходит:

- `$Shield$` → `Shield`: на экране это слово, скобки — оформление;
- `{0}` и `%s` остаются: игра подставит туда значение, и показать плейсхолдер полезнее, чем
  молча выбросить число, которое он обозначает;
- `<...>`, `#var#`, `[bracket]` исчезают — они не рисуются;
- строки, чей `ru` совпал с `en`, пропускаются: это либо законный проброс (число, код), либо
  переводчик сдался и вернул английский. Второе засчиталось бы как покрытие, показывая
  английский, — хуже честного промаха. `--keep-identity` отключает.

Ключ строки синтетический, от хеша нормализованного текста. Без него безключевые строки
вставляются заново при каждом запуске, и база растёт дублями на каждый импорт; с ним повторный
прогон идемпотентен, а изменившийся перевод просто обновляет строку.

Импорт прогнан на настоящих 43 548 переводах: 42 524 строки в базе, 125 отброшенных эхо,
899 схлопнувшихся по одинаковому нормализованному ключу (одна и та же фраза в разной обёртке —
после снятия разметки это честно одна строка, и OCR их всё равно не различил бы), ни одного
уцелевшего тега в отображаемом тексте.

### Полный проход

```bash
cd tools

# 1. Разобраться, где в дампе локализация. Правится руками — tables.yaml источник истины.
#    Сканирует и JSON, и любые файлы с SQLite-заголовком, независимо от расширения.
python import_dump.py --scan --dump ./dump

# 2. Импорт
python import_dump.py --dump ./dump --db ../czn.db --pack "C:/.../data.pack"

# 3. Перевод (сначала память переводов, затем модель)
python translate.py --db ../czn.db

# 4. Проверка и ревью
python validate.py --db ../czn.db
python review.py --db ../czn.db      # http://127.0.0.1:8777

# После патча
python diff_pack.py --dump ./dump-new --db ../czn.db --pack "C:/.../data.pack" --dry-run
```

Экспорт из AssetRipper делается руками — инструмент пока GUI-only, и `import_dump.py` начинает с
уже выгруженной папки (§8). Если строки нашлись в БД, шаг с AssetRipper не нужен вовсе: `--dump`
указывается на папку с базами (в том числе на `./carved`), и дальше всё то же самое.

### Нормализация связывает две половины

`CznTranslator.Lookup.TextNormalizer` и `tools/czn/normalize.py` обязаны совпадать посимвольно.
Расхождение здесь не ломает ничего заметного: импортёр продолжает писать строки, приложение
продолжает работать, строки просто становятся недостижимы с точного шага, и coverage проседает
без единой ошибки в логах.

`tools/tests/normalization_vectors.json` сгенерирован из C# и проверяется **обоими** наборами
тестов — 20 векторов, нормализованная форма, знаковый xxHash64 и вариант без свёртки глифов.
Меняя нормализацию, перегенерируйте файл и прогоните оба набора.

## Что дальше

Порядок работ на Windows, от самого нужного:

1. ✅ `CznTranslator.sln` собирается на Windows — interop под Vortice 3.6.2 починен.
2. ✅ M1 (§10) через `--m1`: click-through прямоугольник поверх окна, слежение за окном, ~60 fps,
   стек DirectComposition/D2D/DWrite поднимается на живом GPU. Осталось подтвердить визуально
   поверх живой игры (borderless).
3. ⚠️ M2 (§10) через `--m2`: модели RapidOCR (`ch_PP-OCRv4_det` + `en_PP-OCRv4_rec` + `en_dict.txt`)
   в `models/`, английский распознаётся корректно. Но цель «det+rec ≤ 30 мс на 400×80» на встроенной
   Intel Iris Xe **не достигнута**: CPU fp32 ≈ 48 мс (прогрев 45 мс), DirectML на iGPU ≈ 136 мс
   (прогрев 31 с); узкое место — rec. Пути к 30 мс: дискретный GPU или int8-квант (профиль laptop —
   готовых квантованных ONNX у RapidOCR нет, надо генерировать). `DbPostProcessor` зовёт нативный
   OpenCV, поэтому добавлен пакет `OpenCvSharp4.runtime.win`.
4. ⚙️ Регрессионный раннер готов: `CznTranslator.exe --frames-test <dir>` прогоняет PNG-кадры через
   det+rec и сверяет распознанное с `<кадр>.expected.json` (поле `en`). Осталось снять сам набор —
   ≥30 кадров с живой игры, включая трудные (полупрозрачный текст, мелкий шрифт, цветные теги,
   скроллящийся список). Проверка `ru`/`source` включится с заполненной БД (§12).
5. ⛔ `probe_pack.py` прогнан по игре: тексты (`text_en`/`text_ko`, рев. 610) лежат в проприетарном
   зашифрованном контейнере `data.pack` (4.2 ГБ чанками; индекс — кастомный `PLPcK` + `.pigz`).
   Встроенного SQLite нет (`--carve` пусто), на диск распакованы только звук и видео. Значит
   **офлайн-предзаполнение по §8 на этой игре недоступно** без реверса формата пака — ни импорт из
   БД, ни AssetRipper не работают напрямую. Практический путь: оверлей на OCR + фолбэк §7, база
   растёт из увиденного (`src='ocr'`).

Отдельно стоит померить, что реально даёт свёртка глифов из §5. Она агрессивна: `boss` → `8055`,
`sos` и `505` схлопываются в один ключ. Симметричность делает её безопасной для точного шага, но
она же огрубляет расстояние Левенштейна на нечётком. `NormalizeOptions.FoldConfusableGlyphs`
существует, чтобы прогнать набор кадров с ней и без неё и сравнить coverage; смена флага требует
переимпорта базы, потому что `norm` и `norm_hash` хранятся.
